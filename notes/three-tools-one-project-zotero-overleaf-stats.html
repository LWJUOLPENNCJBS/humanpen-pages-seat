Three tools and one project: Zotero, Overleaf and a statistics stack versus HumanPen

Most research workflows are a stack, not a product. A reference manager holds the sources, a LaTeX editor holds the manuscript, and a statistical package holds the analysis. Every handoff between them is a place where a number or a citation can drift. This page compares that arrangement with a single plan-first project, without pretending one replaces the other — the honest answer is about which handoffs you can afford.

HumanPen Start Project is described as research, data analysis and professional writing delivered end to end: you say what you need, attach data, and get analysis, charts and a report. It is not a reference manager or a LaTeX editor. The comparison is therefore about workflow shape. The tool's own boundary statements matter: analyses originally done in SPSS or Stata are performed using Python or R, Wind or CNKI data should be exported first, and GPU training is not supported.

A single project is better at a bounded task where the analysis, figures and report must agree with each other at the moment of delivery. Choosing between them is a question about the shape of the work, not about which tool is more capable.

The real cost of the stack is the handoff

A reference manager, an editor and a statistics package are each good at their own stage. The cost appears at the boundaries. A number is copied from an output window into a manuscript. A bibliography is exported and then edited by hand for a journal style. A figure is regenerated after a data correction and the old one is still in the submission. None of these are tool failures; they are translation failures between tools.

HumanPen's starting point addresses one of them. The page describes a data report, clinical-trial statistics, a research paper and group-meeting slides as example outputs of the same project. The review example states that a primary endpoint matches, populations add up, a rerun reproduces the results, and references were found one by one. That is a check across stages, which is exactly what a stack has to do manually.

But the stack has an advantage a single project does not: each component can be replaced. If you need native SPSS replay, keep SPSS. If your field requires a specific LaTeX class, keep Overleaf. The tool does not claim to be a library or an editor, and that is a reasonable boundary rather than a weakness.

Where the plan-first model earns its place

The strongest case for a single project is a task with a clear deliverable and a deadline: a re-analysis of a published table, a clinical statistics report, a first draft from a dataset, a set of slides for a defence. The public workflow is explicit. You describe the task and attach files, the system confirms requirements and proposes a plan, work starts only after your approval, and a second check runs before reports, charts and code are delivered.

That sequence replaces a chain of informal handoffs with one written agreement. If the plan names the endpoint and the population, you can hold the delivery against it. If a revision is needed, the scope is explained before work starts, a new version is delivered and past versions are kept. A stack can do this, but only if the team enforces the discipline; here the discipline is the product.

For API users the same shape is available. The developer page describes a project with a state and a stage, a required-input field while it waits for you, a plan you confirm by naming its version, and a delivery downloaded from a short-lived signed URL. Autonomy can run a project within a credit cap, and a webhook names only the project and its state. That is a fit for automated pipelines, not a reason to abandon a reference library.

What to put in the plan so the handoffs stay small

The quality of the project delivery is bounded by the quality of the first message. Name the population, the endpoint, the output format and the target convention in the request itself, the way you would brief a colleague. If you want three-line tables and captions, say so. If the report must be a Word file with the code alongside, say so. The public FAQ states that AI confirms requirements and proposes a plan before work starts, so the first message is where those decisions get fixed.

Attach the data dictionary with the files. A coded variable without its codebook is the classic handoff failure in a stack, and it is no less a failure inside a single project. The example project names its analysis set and explains how missing outcomes are handled; that level of specification is what you should aim for in the request. The plan you approve then becomes the acceptance criterion against which the delivered report, charts and code are checked.

The honest limits before you commit

Three limits are stated plainly and should shape the decision. First, analysis runs on Python or R; work originally done in SPSS or Stata is re-performed, not replayed. If your reproducibility requirement names the original package, a single project cannot satisfy it alone. Second, Wind and CNKI exports must be prepared first. Third, GPU training is not supported — this is a document and research-data service, not a training environment.

Retention is a fourth consideration. Projects are kept for six months after the last activity, with a reminder three days before expiry, and can be deleted at any time. A stack that writes into your own version-controlled repository is permanent by default. For a long-running thesis, the repository remains the system of record and the project is a workspace you export from.

None of this argues against the project. It argues for using it for what it is: a bounded, checkable workspace for analysis and writing, with an explicit plan and a version history.

A practical division of labour

Keep Zotero or your equivalent as the library. Keep Overleaf if your target venue expects LaTeX or your equations demand it. Use the statistical package when native replay is required. Then identify the bounded deliverables in the project plan — the re-analysis, the evidence table, the draft, the slides — and run those as projects. Export the results into your own repository and your own editor for final assembly.

This division keeps each tool doing what it is good at and reduces the handoffs that matter most. The-output check is simple: after delivery, verify that the endpoint in the report matches the plan, that the populations add up, that the rerun reproduces the result, and that the references are all found. If those four hold, the analysis-to-report handoff survived.

Frequently asked questions

Does Start Project replace Zotero?

No. It keeps citations unchanged in a document and can check references found in a delivered project, but it does not maintain a shared reference library with metadata and de-duplication.

Can it write LaTeX directly?

The described deliverables are Word reports, editable PowerPoint slides, code, figures and comparison documents. If your venue requires a LaTeX source, keep an editor for final assembly.

What languages does the analysis run in?

Python or R. Analyses originally done in SPSS or Stata are performed using Python or R, and code is delivered.

What happens to my project after delivery?

It is kept for six months after the last activity, with a reminder three days before expiry, and can be deleted at any time. Export what you need to keep permanently.

Can I automate the whole flow through the API?

Yes, within stated limits. A project can confirm plans and answer questions under a credit cap, with a webhook naming only the project and state. API keys belong in backend services, not browsers or public repositories.
