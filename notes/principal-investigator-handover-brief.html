A principal investigator's handover brief: what to write down before HumanPen Start Project touches your data

The analysis is rarely what goes wrong on a delegated project. The brief is. An endpoint gets inferred from a column name, the population is decided by whoever happens to have a complete record, and weeks later the table is technically correct and the question is wrong. A written handover brief costs an hour and is the only artefact that survives the handover.

This page is the version we would hand to a principal investigator who is about to give a dataset to HumanPen Start Project, to a statistician, or to a postdoc with six weeks left on their contract. It is written from the delivery side: every item below is something a reviewer checks, so writing it down now removes a revision round later.

1. Write the question as a sentence with a comparison in it

"The data are about aspirin in acute ischaemic stroke" is a topic. "In the full analysis set, does aspirin change death or dependency at six months compared with control" is a question. Only the second one tells an analyst what to compute, what to hold constant and what to put in the first table.

If you cannot write the comparison in one sentence, that is the finding to act on before any analysis starts. It is much cheaper to discover a vague question in a planning conversation than in a results section.

2. Say what counts as a patient

Every percentage in the report is a fraction, and the denominator is a decision. Write down the inclusion criteria, the exclusion criteria, and the order in which they are applied. Then write down the name you want for the resulting set, because names leak into tables: a full analysis set, a per-protocol set and a safety set are three different denominators and they should never be called "the sample".

HumanPen Start Project's public example is explicit about this. The demonstration project describes a full analysis set of 19,435 patients with a primary endpoint of death or dependency at six months, and about 150 missing outcomes handled in a sensitivity analysis. That sentence is only meaningful because the set, the endpoint and the missing-data handling were all named.

3. Fix the endpoint and the timepoint together

An endpoint without a timepoint is ambiguous, and a timepoint without an endpoint is a date. Write both, and write how the endpoint is derived: which source variables, which rule for ties, what happens to patients who were lost before the assessment.

Where the endpoint is a composite, spell out the components. Where it is a scale, spell out the cut point and the direction of benefit. A reviewer who has to guess will guess differently from you.

4. Declare the history of the dataset

Datasets accumulate history: a correction applied in March, a duplicate block removed in April, a variable recoded after a query. If the history is not written down, the analysis reruns the mistakes. Include the file you consider canonical, the date it became canonical, and a one-line reason for every change you know about.

This is also where you record what has already been run and rejected. A previously attempted model that failed for a known reason is useful information, not an embarrassment; it stops the same model being tried again under a new name.

5. Pre-specify the contrasts you intend to report

List the comparisons you will put in the paper, and separate them from the ones you are curious about. Pre-specified contrasts can be reported as confirmatory. Everything else is descriptive, and the wording in the results section should say so.

The same discipline applies to subgroups. A forest plot is an efficient way to display heterogeneity; it is not evidence that any single subgroup difference is real.

6. Attach the codebook, not just the data

A column called sex is unambiguous. A column called grp is not. Send the codebook or the questionnaire, the units, the missing-value conventions, and the labels for every categorical variable. If the codebook lives in someone's head, write those sentences down now — that person may be unreachable by the time the analysis runs.

HumanPen Start Project accepts Excel, CSV, Word, PDF and zip files up to 5 GB total, and analyses run in Python or R; work originally done in SPSS or Stata is re-done in Python or R rather than executed in the original package. That last point matters for handover, because it means your brief should say what the original analysis did, not which menus were clicked.

7. Say what the deliverable must contain

Write the delivery list before the work starts: the report document, the tables, the figures at the resolution your journal requires, and the code. HumanPen Start Project delivers a .docx report, figures, code, and slides with speaker notes where slides are part of the job; its public example cites figures at 300 dpi, three-line tables with captions, and a report whose numbers and citations are kept exactly as computed.

If your target journal wants a specific table style, say it in the brief. If your institution wants the code archived, say it in the brief. Requirements discovered after delivery are the expensive kind.

8. Use the plan step as a contract review, not a formality

HumanPen Start Project works on a plan-first rule: it confirms requirements, proposes a plan, and starts only when you approve the plan. That approval is the moment where a misread brief is still cheap. Read the plan as if a colleague had written it, and check three things: does it name the same population you did, does it name the same endpoint and timepoint, and does it list the same deliverable you expect.

If any of the three is wrong, correct it there. Approving a plan you have not read converts a planning conversation into a revision request.

9. Check the delivery against four concrete tests

On delivery, run the same four checks the product's public example reports from its independent review: the primary endpoint matches the stated numbers (in the published example, 62.2% against 63.5%, P = 0.072), every analysis population adds up, a clean rerun reproduces the results exactly, and all 11 references are found one by one.

Those four checks are not a substitute for statistical judgement. They are the floor: they catch the failures that make a report unusable regardless of how good the modelling was.

Frequently asked questions

Do I need to write a full protocol before starting?

No. You need a page that names the question, the population, the endpoint and its timepoint, the pre-specified contrasts, the codebook and the deliverable. A protocol is a governance document; a handover brief is a working document, and the working document is what prevents rework.

What if my endpoint definition changes after I see the results?

Then say so, and label the analysis accordingly. Changing an endpoint after seeing data is a decision with consequences for how the result can be described; hiding the change is worse than making it.

Can I hand over data before the brief is finished?

You can attach files early, but expect the plan to be provisional until the brief is complete. HumanPen Start Project asks for confirmation of requirements before work starts, and an incomplete brief is exactly what that step is designed to surface.

Who owns the analysis once it is delivered?

You do. The deliverables include the code, and projects can be deleted completely at any time, so the report does not depend on continued access to the service. Archives are kept for six months after the last activity with a reminder three days before expiry, which is a retention default rather than a lock-in.
