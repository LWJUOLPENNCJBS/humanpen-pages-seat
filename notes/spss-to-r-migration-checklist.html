Moving an SPSS analysis to R: the migration checklist we use on HumanPen Start Project jobs

Almost every SPSS analysis that arrives for re-doing comes with the same request: keep the results, change the tool. That is the wrong framing. The results are a consequence of a hundred small decisions that SPSS makes silently — listwise deletion, the reference category, the way a value label overrides a number. Migrating means re-deciding those explicitly, then proving that the new decisions reproduce the old output.

This is the checklist we apply when an SPSS job is re-done in R on HumanPen Start Project, which states plainly that analyses originally done in SPSS or Stata are performed using Python or R. It is written so that you can run the same check on your own migration.

1. Inventory the file before you migrate anything

Open the .sav and write down four things: the number of cases, the number of variables, every user-defined missing code, and every variable whose label differs from its name. The last two are where migrations break. A code of 99 that means "unknown" will be read as ninety-nine by any tool that is not told otherwise, and a variable labelled "income band" with values 1–5 is not a continuous measure.

Produce a codebook from this inventory and keep it with the data. In a HumanPen Start Project job the codebook travels with the files in the same upload rather than being reconstructed afterwards.

2. Decide where labels live

R has no equivalent of the SPSS value-label layer, so you must choose: convert labels into factors, keep numeric codes and carry a lookup table, or both. The choice has consequences. Factors protect you from analysing a code as a quantity, but they also change model output, because the first level becomes the reference.

Write the reference level down explicitly. A migration that silently changes the reference group produces the same model with different coefficients, which is the most confusing kind of difference to debug.

3. Make missingness a written rule

SPSS excludes cases listwise by default in most procedures, and the exclusion is invisible in the output. In R the same behaviour has to be requested, variable by variable, and the count of excluded cases should be printed rather than assumed.

For each variable, record one of: never missing, missing means not applicable, missing means unknown, or missing is a category. Then state what the analysis does with each. A sensitivity analysis is only meaningful if the main analysis's rule is written down; the public HumanPen example makes this explicit with about 150 missing outcomes handled in a sensitivity analysis against a full analysis set of 19,435 patients.

4. Rebuild split and select as code

Split file and select cases are the two SPSS features that most often hide in someone's memory rather than in the syntax. Enumerate every subgroup you intend to report, then produce them from one grouped operation so that the subgroup counts are visible and reconcile with the total.

If the subgroup counts do not sum to the parent, stop. That is a finding about the data, not a formatting issue.

5. Write out every default

SPSS runs procedures with defaults that are rarely stated: the handling of ties, the confidence level, the method for estimating standard errors, the treatment of zero cells. In R each of these is an argument. The migration is complete when every argument is either default-by-explicit-choice or set deliberately.

Keep a table of the decisions with a one-line reason each. It becomes the methods paragraph, and it is also the thing that makes the next migration faster.

6. Prove parity with a tolerance, not with an impression

Rerun both analyses and compare numbers as numbers, not as screenshots. Compare, in this order: case counts, then descriptive statistics, then model coefficients and standard errors, then p-values. Differences in p-values without differences in estimates mean a different test or a different degrees-of-freedom convention, which is a decision to document rather than a bug.

State your tolerance before you compare. Exact equality is achievable for counts; estimates may differ in the last digit because of numerical libraries, and a stated tolerance turns an argument into a check.

7. Rebuild tables from the model, not from the output

The SPSS pivot table is a rendering of results. In R you build the table from the model object, which means you control the decimals, the ordering and the labels. This is an improvement, but it is also a risk: a hand-built table can disagree with the text if either is edited later.

Generate the table in the same script that fits the model, and let the document take its numbers from the script. HumanPen Start Project delivers three-line tables with captions as part of the deliverable, which is where the journal's table conventions get applied.

8. Re-run from scratch, in a fresh place

The final check is the one that decides whether the migration is real: run the whole pipeline from the original data file in a clean environment, with no leftover objects, and confirm that every number in the document is reproduced.

A clean rerun that reproduces the results exactly is one of the four review items HumanPen Start Project reports on delivery. It is a stronger claim than "the numbers look the same", and it is the only one worth making.

Common failures, and the one-line fix

The reference category flipped: declare factor levels in the order you intend, and print them in the methods. Missing data treated as a value: recode before any summary, and print the missingness table first. Weighted analysis run unweighted: pass the weight argument at every model, not once at the top. Duplicate rows from a merge: check the join keys and assert uniqueness before joining. Rounding applied twice: round once, at the table, never in the data.

Frequently asked questions

Can I keep using the SPSS syntax file as documentation?

Yes, as documentation of what was done, not as an executable specification. Keep it in the archive next to the new script, because it is the record of the original decisions that the new code is trying to reproduce.

Do the labels survive the migration?

Only if you carry them deliberately. The safe pattern is to convert labels into a codebook and into factor levels in the script, then verify that the rendered tables show the same words the original tables showed.

What if the new numbers differ from the published ones?

Find the decision that differs before deciding which is right. The usual candidates are a filter, a recoded value, a missingness rule, a weight, or a reference level. Each of those has a documentary answer.

Does this work for a thesis committee that expects SPSS output?

The deliverable is a report with tables, figures and code, not a .spv file. If a committee requires the original software's output specifically, that is a requirement to state before the work starts rather than a difference to discover afterwards.
