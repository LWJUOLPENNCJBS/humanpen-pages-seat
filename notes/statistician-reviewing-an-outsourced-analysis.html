How a statistician reviews an outsourced analysis: a checklist that works on HumanPen Start Project deliverables

Reviewing someone else's analysis is a different job from doing the analysis. You are not looking for the best model; you are looking for the places where the report can be wrong without looking wrong. The order matters, because a report that fails on population arithmetic does not need its regression diagnostics read.

This checklist is the one we would use on a HumanPen Start Project delivery, and on any other delivery that arrives as a document plus figures plus code. It assumes the reviewer has thirty minutes and no access to the analyst.

The order of checks

OrderCheckWhat you are actually testingCost of skipping it
1Population arithmeticWhether every table's N is a subset of a defined set, and whether the subsets sum correctlyEvery downstream percentage inherits the error
2Endpoint definitionWhether the analysed endpoint is the protocol's endpoint, at the protocol's timepointThe paper answers a different question convincingly
3Missing data handlingWhether exclusions are counted, described and tested for sensitivitySilent bias in the headline estimate
4Model specificationWhether covariates, functional form and clustering match the designStandard errors that are too small
5ReproducibilityWhether a clean rerun returns the same numbersA result nobody can defend under query
6Figures and tablesWhether the visual claim matches the tabulated claimA figure that oversells a null result
7CitationsWhether each cited claim exists and says what it is cited forRetraction risk at the worst moment
8Language of certaintyWhether the prose claims more than the test supportsReviewer objection that is entirely avoidable

1. Start with arithmetic, not with statistics

Before reading a single estimate, find every N in the document and place it in a hierarchy. The full analysis set should be the largest number, every subgroup should be a subset of it, and every subgroup partition should sum to its parent. When the numbers do not reconcile, the cause is usually an undocumented exclusion rather than an error in the model.

HumanPen Start Project's public example makes this checkable by listing it as one of four review items: every analysis population adds up. That is the right level of ambition for a first pass — not "the statistics are correct", but "the accounting is correct".

2. Confirm the endpoint is the endpoint

Read the endpoint definition in the methods, then read what the results actually computed. Look for three common drifts: a composite endpoint reported as if it were a single component, a timepoint silently replaced by the nearest available assessment, and a continuous variable dichotomised at a cut point that appears nowhere in the protocol.

In the published HumanPen example the primary endpoint is death or dependency at six months, and the report's first check is that the primary endpoint matches: 62.2% in the aspirin group against 63.5% in the control group, P = 0.072. Notice what that sentence does — it pins the endpoint, the timepoint, the groups and the test in one line, so a reviewer can compare it against the protocol without hunting.

3. Read the missing data section as a list of decisions

Missing data is not a nuisance to be mentioned; it is a set of decisions. Count them: how many patients were excluded, on what variable, at what stage, and what happened to the estimate when they were handled differently. A sensitivity analysis is only reassuring if it is described well enough to be repeated.

The public example states that about 150 missing outcomes are handled in a sensitivity analysis, against a full analysis set of 19,435 patients. Whether or not you agree with the handling, the number is on the page, which means the reviewer can ask a specific question instead of a general one.

4. Match the model to the design

Check that the covariates are the pre-specified ones, that clustering follows the unit of randomisation, that the functional form is either justified or shown to be insensitive, and that any interaction was pre-specified rather than discovered. If the design is a trial, the analysis should look like a trial analysis; if it is a survey, the weights should appear somewhere.

A specification that cannot be justified in one sentence is usually a specification that was chosen after looking at the fit.

5. Insist on a clean rerun

Ask for the analysis to be re-run from the delivered data and the delivered code, in a fresh environment. The test is not whether the numbers are close; it is whether they are identical. Differences that are "within rounding" are a signal that something in the pipeline is not deterministic — a random seed, a sort order, a filter applied in one script and not another.

HumanPen Start Project states this as its third review item: a clean rerun reproduces the results exactly. If an analyst cannot demonstrate that, the correct conclusion is not that the result is wrong, but that nobody currently knows whether it is.

6. Compare figures against tables, not against expectations

For every figure, find the table cell that contains its numbers. A confidence interval that crosses the null in the table should not look like a clear effect in the figure; a subgroup with wide intervals should not be drawn at the same visual weight as the overall estimate. Axis truncation, log scales and dual axes are the three places where an honest figure can still mislead.

HumanPen Start Project's delivery list includes 300 dpi figures and three-line tables with captions, which is a format claim rather than a correctness claim — but format matters here, because a caption is where the reader learns what the error bars represent.

7. Check citations mechanically, then read them

Mechanical first: does each reference resolve, is the year consistent with the volume, is the DOI real. Then substantive: does the cited paper support the sentence it is attached to. The second check is the one that catches the most damage, and it is also the one most often skipped under time pressure.

The published example reports the mechanical version as its fourth item — all 11 references found, one by one — and separately mentions a PubMed search with every DOI checked. That is the minimum. It does not certify that every citation is apt.

8. Audit the language of certainty

Finally, read the discussion and count the verbs. "Suggest", "are consistent with" and "show" are three different claims. A null result reported as "no effect" rather than "no evidence of an effect" is a factual overreach that a careful reviewer will catch, and it is the easiest thing in the document to fix before submission.

What to write in the review

A useful review has three parts: what you verified and how, what you could not verify and why, and the specific changes required. Vague approval is the failure mode; a report that has been read carefully and approved specifically is worth more than a report that has been rewritten twice.

HumanPen Start Project's revision flow fits this shape: revisions are requested in the project, the scope is explained first, work starts after you confirm, and a new version is delivered while past versions are kept. That means a review comment can be answered with a diff rather than with a new document.

Frequently asked questions

How long should a review take?

Longer than the delivery took to read, and shorter than the analysis took to run. For a report with a handful of tables, an experienced reviewer can complete the eight checks above in a single sitting; the expensive part is the citation reading, which scales with the number of claims rather than with the size of the document.

Is it a problem that the code was written by an AI?

It is a problem if nobody can read it. The relevant question is whether the code can be inspected, re-run and modified by a human who understands the design. HumanPen Start Project delivers the code with the report, and the analysis runs in Python or R, which are both inspectable by any statistician who works in either language.

What if the delivered numbers differ slightly from my own earlier run?

Find out why before deciding which is right. A difference usually comes from one of four places: a filter applied differently, a different version of a variable, a different missing-data rule, or a random seed. Each of those is a documentation gap, and each is worth closing.

Can I check the analysis without the raw data?

Partially. You can check arithmetic, consistency between tables and figures, the language of certainty, and citations. You cannot check the model without the data, which is why the data and the code should travel together with the report.
