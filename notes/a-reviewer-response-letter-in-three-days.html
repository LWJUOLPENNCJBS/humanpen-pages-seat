A reviewer response in three days: triage, re-analysis and the letter, with HumanPen Start Project

Reviewer comments arrive as prose and are answered as prose, which is why so many response letters are long, defensive and unconvincing. The work is not writing. The work is deciding, for each comment, what evidence would settle it — and then producing that evidence without disturbing the numbers the paper already reports.

This is the procedure we would use to turn a set of reviews into a response letter in three days, with HumanPen Start Project handling the additional analyses.

First day, morning: copy the comments verbatim

Build the table before you form an opinion. One row per comment, quoted exactly, with the reviewer number and the section of the paper it concerns. Paraphrasing at this stage is how a caveat becomes a demand and a suggestion becomes a condition.

Then add a column for what the comment presupposes. Many comments carry an assumption — that the sample was smaller, that a test was two-sided, that a variable was measured differently — and correcting the assumption is a legitimate response.

First day, afternoon: classify before you compute

Three classes. Evidence comments require new analysis or new data. Wording comments require a change in the text, and are cheap. Disagreement comments require an argument, and should be rare and clearly labelled.

Sort by class, then by cost. Do the wording changes first, because they are certain to be accepted and they clear the letter's structure. Do the disagreement last, because writing them well requires knowing what the new evidence shows.

A fourth class is worth naming: comments that cannot be answered, because the data were not collected. Say so early and clearly, with what was collected instead.

Second day, morning: specify the additional analysis as a plan

For each evidence comment, write the analysis that would settle it: the population, the endpoint, the model, and the table you expect. Then hand that specification over.

This is where HumanPen Start Project's plan-first rule is useful under time pressure. The plan states what will be run before anything runs, so a misread comment is caught in the plan rather than in a table you have already inserted into a manuscript. Read the plan against the comment, not against your hopes.

Two constraints to state in the brief. First, the new analysis must use the same data version as the paper, otherwise the new table will not reconcile with the old ones. Second, the deliverable must include the code, because a reviewer may ask how the sensitivity analysis was computed.

Second day, afternoon: audit the delta

When the analyses come back, build a delta table: for every table and figure in the paper, did the number change, and if so why. A number that changes without a stated reason is a defect in the revision, and reviewers notice.

If an additional analysis changes a conclusion, that is a finding worth reporting honestly. A revision that says "the sensitivity analysis weakened the effect, and we have revised the abstract accordingly" is stronger than one that reports only the analyses that agreed.

HumanPen Start Project's review items apply here too: every analysis population adds up, the endpoint matches, and a clean rerun reproduces the results exactly. Run those three checks on the new tables before you write a single sentence about them.

Third day, morning: write the letter in the reviewers' order

Structure each response as: the comment verbatim, a one-sentence answer, the evidence, and the change with a location. Answer first. Reviewers read dozens of these; the sentence that begins "We thank the reviewer for this insightful comment" delays the answer without adding information.

Where you disagree, disagree in one paragraph: what the comment assumes, what the analysis shows, and what you have changed anyway in the interest of clarity. Where you comply, say exactly where.

Keep a version map. HumanPen Start Project delivers revisions as new versions while keeping the old ones, and if a reviewer asks what changed between rounds, that history is the answer.

Third day, afternoon: reconcile the manuscript and the letter

Read the letter and the manuscript together and check every quoted number, every section reference and every new table label. Then check the abstract, because the abstract is where a revision most often fails to follow the results.

Finally, check the references again. A revision that adds a table usually adds a citation, and the mechanical check that all references resolve is worth repeating at this stage.

What the letter should not do

It should not re-litigate the paper's importance. It should not describe an analysis that was not run. It should not use the phrase "we respectfully disagree" without an argument after it. And it should not exceed the journal's stated format for responses, because a letter that ignores the format is a letter that signals the paper ignored the format too.

The cover letter is one paragraph, and it is not a summary

Editors read the cover letter to decide whether the revision is worth a second round. It should say what changed at the level of the argument, not at the level of the file: which comments led to new analyses, whether any conclusion moved, and where the manuscript is now stronger.

Three sentences is usually enough. "The additional sensitivity analysis requested by reviewer two now appears in table four; it does not change the direction of the estimate, and we have added the limitation to the discussion. Reviewer one's point about the reference category was correct and we have re-run the model with the stated reference. The remaining comments are addressed point by point." That is a cover letter.

What it should not do is repeat the response letter. The editor will read the letter; the cover letter's job is to make that reading cheaper.

When the analysis takes longer than the letter

If a requested analysis will not finish inside the window, ask the editor for an extension before the deadline rather than submitting a letter that promises work in progress. Extensions are routine; a response that describes an analysis the paper does not contain is not.

If the extension is refused, submit what you have, state plainly which analysis is outstanding, and explain what it would test. Editors can work with a stated gap. They cannot work with an implied result.

Frequently asked questions

What if the reviewer asks for an analysis the data cannot support?

Say what the data can support, run that, and state the limitation explicitly in the response and in the manuscript. Reviewers accept bounded answers far more often than they accept a confident answer to a different question.

Can the additional analysis be run in the same project as the original?

Yes, and that is usually better: the same project holds the same data version, so the new tables reconcile with the old ones. A revision in the same project is delivered as a new version with the earlier versions kept.

How much detail should the response include?

Enough that a reader can verify the claim without opening the manuscript. For an analysis, that means the specification, the result and the location of the new table.

What if the two reviewers disagree?

Say so, and explain the decision you made. An editor is used to adjudicating between reviewers; what an editor cannot adjudicate is a letter that pretends the disagreement does not exist.
