Moving a Stata analysis to Python: a migration checklist for HumanPen Start Project jobs

A Stata project is usually a folder of .do files that were written over several years by several people, each of which assumes the dataset in memory is already in a particular state. That assumption is the thing that breaks in migration. The models are portable; the sequence of preserve, restore, merge and drop calls around them is what has to be reconstructed.

This is the checklist we apply when a Stata analysis is re-done in Python on HumanPen Start Project, whose public page states that analyses originally done in SPSS or Stata are performed using Python or R. It is written to be run by the person who has to defend the numbers afterwards.

1. Reconstruct the state machine before porting the models

Read the .do files in order and write down what each one assumes about the dataset in memory. Most projects have three or four implicit states: raw, cleaned, analysis-ready, and a subsample used for a robustness check. Draw those states as a list of named datasets, then port each transition as a function.

The migration is finished when each state is a named artefact you can produce independently, rather than a side effect of having run the previous section.

2. Handle missing values explicitly

Stata's . propagates through arithmetic and is excluded from most estimators by default. In Python, NaN also propagates but estimators differ in whether they drop or fail, and pandas operations differ in whether they skip. Decide per variable: never missing, structurally missing, unknown, or a valid category.

Then print the missingness table first in every report. It is the cheapest defence against a reviewer's question about who was excluded.

3. Carry the label layer into a codebook

label define is a layer that most Python code drops. Keep it: export the label sets into the codebook, and encode categorical variables so that the rendered tables show labels rather than codes. Verify by comparing a frequency table built from the new pipeline against the original one, label by label.

This is also the step where a silently recoded category gets caught, because the label comparison surfaces a shifted code.

4. Port reshapes as named operations

preserve and restore are a manual stack. reshape wide/long is a named transformation. In Python both become functions with explicit keys and explicit outputs, which is better, provided the keys are asserted: check that the wide form has one row per unit, and that long-to-wide-to-long returns the original frame.

Most migration errors in panel data are reshape errors, and they are invisible in the final table because the model still runs.

5. Write out the estimation options

Stata's estimators carry defaults that the .do file may not mention: the covariance estimator, the clustering, the treatment of singleton groups, the base level of a factor variable. In Python each is an argument. Enumerate them, choose deliberately, and record the choice with a one-line reason.

Where the original used a prefix such as a survey prefix, port it as a design declaration rather than as an option on the model, so that every model in the script inherits the same design.

6. Recompute post-estimation quantities from the model

Margins, linear combinations and joint tests are where migrations most often produce plausible but wrong numbers, because they are computed after the model and depend on the covariate values chosen. Recompute them explicitly, and compare against the original output value by value, including the confidence intervals.

If a margin differs while the coefficients match, the difference is in the evaluation point or in the delta-method convention, not in the model.

7. Build tables from model objects

Generate the table in the same script that fits the model, so the document's numbers cannot drift from the analysis. HumanPen Start Project delivers three-line tables with captions and figures at 300 dpi, which is where journal conventions are applied; the numbers in those tables should come from the model objects rather than from a spreadsheet intermediate.

8. Prove parity with stated tolerances

Compare in this order: counts, descriptives, coefficients, standard errors, test statistics. Declare a tolerance in advance. Exact equality for counts; last-digit tolerance for estimates where numerical libraries differ. A difference that exceeds the tolerance is a decision to find, not a rounding error to accept.

The final gate is a clean rerun: the whole pipeline from the original file, in a fresh environment, reproducing every number in the document. HumanPen Start Project reports exactly this as one of four review items, alongside the check that every analysis population adds up.

What tends to go wrong

The working directory is the first casualty: .do files assume the operator's folder, and scripts need paths passed in. Version drift is the second: behaviour changes between releases, so the original output should be regenerated in the original version before it is used as the parity target, or the difference will be attributed to the wrong cause. String encodings are the third: a label with a non-ASCII character can change shape between systems, and the table will show it.

Estimates that cannot be compared directly

Some quantities are not portable at all: a stored estimation result, a saved margin, a hand-computed statistic pasted into a table. For those, the migration has to reconstruct the formula rather than the command. Write the formula in the methods note, compute it in the new script, and compare the value with the original output.

Where the original value cannot be reproduced, the honest outcome is a documented discrepancy: what the old analysis computed, what the new one computes, and which one the paper should report. That sentence is far more defensible than a silently updated table.

Frequently asked questions

Can I keep the .do files as the specification?

Yes, as a record of intent and of the original decisions. Archive them next to the new pipeline, because they are the only evidence of what the earlier analysis did when the two disagree.

Do I need to reproduce the original output exactly?

You need to reproduce it, then explain any deliberate difference. An unexplained difference is a liability; a documented improvement, such as a corrected missing-data rule, is a contribution.

What about commands with no direct equivalent?

Some post-estimation routines have no one-to-one replacement. In that case the honest migration is to compute the quantity from first principles in the script, show the formula, and compare the result with the original output. That is more defensible than importing a package whose conventions you cannot inspect.

Does the delivered project include the code?

Yes. HumanPen Start Project delivers the report, figures, tables and code, and the analysis runs in Python or R, so a reader who works in either language can inspect what was done rather than infer it.
