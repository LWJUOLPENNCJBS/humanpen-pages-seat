Three analysts, one dataset: version discipline that holds up on HumanPen Start Project

When one person analyses a dataset, version control is a preference. When three people do, it is the only thing standing between a defensible result and a table whose provenance nobody can reconstruct. The symptoms are familiar: two files with the same name, three different Ns, and a figure that cannot be regenerated.

This is the discipline we would impose on a shared project, whether the analysis is run by a team, by a student and a supervisor, or by one analyst plus HumanPen Start Project.

The version events that must be recorded

EventWhat must change in the recordWhat must not change silently
New raw data arriveA new raw file name, dated, with what was addedThe canonical analysis file, until the merge is verified
A correction is appliedA dated note with the reason and the affected rowsThe old file, which must remain retrievable
A variable is recodedA codebook entry with the old and new codingThe definition of any outcome already reported
The population changesA new named population, with inclusion rules statedThe denominators in tables already circulated
A model is re-specifiedA note naming the previous specification and why it changedThe results already quoted in a draft
A table is regeneratedA diff of the numbers that movedAny number without an explanation
A deliverable is supersededThe version number and the date of supersessionThe previous version, which reviewers may ask about

One file is canonical, and it says so in its name

Adopt a naming rule and never break it: a canonical file carries a date, a short reason, and no words like "final". "Final" is a lie within a week. The canonical file is the only file any analysis may read, and every derivative is produced by a script rather than by hand.

Then write one sentence in the project brief: this file, this version, this date. When someone asks which numbers are current, the answer is a file name rather than a recollection.

Publish the denominators before the models

Before anyone fits a model, agree on the population definitions and print the counts. Every table in every deliverable must then reconcile with those counts, and any table that does not is a defect rather than a variation.

This is the earliest possible check and it is the one that catches the most. HumanPen Start Project reports "every analysis population adds up" as one of its four review items, which is the same rule applied inside a single delivery; across three analysts, it needs to be applied across deliveries.

Separate the data decision from the model decision

Two people disagreeing about a model is normal. Two people disagreeing about which rows are in the dataset is a governance failure. Keep the two conversations apart: data decisions get a dated entry in the log and an owner; model decisions get a note in the analysis plan.

When a model change implies a data change, it needs both entries. That is the case where provenance is most often lost.

Make reruns the unit of trust

The rule that survives personnel changes is this: a result is current if a clean rerun from the canonical file reproduces it. Not "if the file exists", not "if the analyst says so".

HumanPen Start Project's fourth review item is the same idea in miniature — a clean rerun reproduces the results exactly — and its delivery keeps past versions when a revision is made. Together those two properties give a shared project something it usually lacks: a way to say what the numbers were on a given date.

When the numbers move, say why in one line

Every regenerated table should come with a one-line diff note: what moved, by how much, and why. "Table two: N fell from the full set to the complete-case set after the missingness rule changed; estimate moved from X to Y" is sufficient. Without the note, the next person will assume an error.

Where a number moves in a way that changes a conclusion, that is not a diff note; it is a decision that needs the whole team, and usually the supervisor.

Give each analyst a named scope

Parallel work fails when scopes overlap. Assign sections rather than files: one person owns the descriptive tables, one owns the models, one owns the figures. Each output is generated by one script owned by one person, and the shared file is read-only for everyone.

If two people must touch the same script, one of them waits. That is cheaper than reconciling two divergent versions of the same model.

Hand the discipline to the API when work is delegated

If part of the analysis is delegated to HumanPen Start Project, the version discipline becomes an interface. The project takes files, returns a plan, and produces a report plus code; the API exposes project state and events, and uploads are explicit steps rather than a shared drive. That means a delegated analysis has a stated input set — which is exactly the property that a shared drive destroys.

State the canonical file's identity in the brief, including its date, and ask for the analysis to be run on that version. Files can be uploaded up to 5 GB total, so the raw exports and the codebook can travel with the analysis file rather than being reconstructed later.

When the log and the code disagree

They will disagree, and the code wins as evidence while the log wins as intent. The procedure is to read the code, describe what it actually does, compare that with the log entry, and then decide which is right. Usually the code is right and the log is stale; occasionally the log records a decision that was never implemented, which is the more serious case because a reported result may not include it.

Record the resolution as a new dated entry rather than editing the old one. The log is an audit trail, and an audit trail that has been tidied is no longer one.

What "reproducible" means when three people are involved

It does not mean that everyone can run everything. It means that for every reported number there is one named script, one named input file and one named person who can run it. That is a smaller and much more achievable standard than a fully automated pipeline, and it is the standard that survives a staff change.

Write the mapping as a table with three columns: reported number, script, owner. Keep it next to the log. When a query arrives, the table answers it in a minute instead of a week.

Agree what counts as a change, before it happens

Write down, at the start, which changes require everyone's agreement and which are individual decisions. In most projects the split is: data inclusion rules, outcome definitions and the headline model require agreement; figure styling, table ordering and text wording do not.

That single distinction prevents most of the friction, because disagreements about styling get treated as disagreements about results when no such distinction has been made.

Frequently asked questions

Do we need git for a shared dataset?

Git is good for scripts and bad for large data files. The workable pattern is version control for code, dated filenames plus a checksum for data, and one log for decisions. The log is what people actually read.

What if a co-author sends a corrected file mid-analysis?

Treat it as a new version event: name it, date it, record what changed, and re-run. Do not overwrite the file that the current draft was produced from, because the draft's numbers must remain explainable.

How do we know which version a published paper used?

Write it down at submission: the canonical file name, the date, and the delivered report's version. That single line answers most post-publication queries.

Is this overkill for a small project?

The cost is one log file and one naming rule. The alternative is a reviewer asking a question that nobody in the lab can answer, which is more expensive than either.
